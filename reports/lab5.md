# 实验五：并发与同步

## 一、实现功能总结

实现进程级死锁检测开关，分别维护互斥锁和信号量的可用资源、已分配资源和待申请资源。申请前模拟线程完成顺序，无法全部完成时撤销请求并返回 `-0xDEAD`。覆盖阻塞锁、自旋锁、信号量唤醒时的资源交接以及条件变量释放和重获锁；线程退出时清理对应记录。迁移 `sys_get_time`，检查用户写权限并支持跨页写回。

## 二、实现与验证记录

### 1. 资源分配及死锁检测

`ProcessControlBlockInner` 持有两份 `DeadlockDetector`，分别供本进程的互斥锁、信号量共享。互斥锁创建时登记 1 份资源，信号量按创建参数登记许可数。条件变量保存等待队列，资源记账发生在它使用的互斥锁上。

申请时先增加 `Need[tid][resource]`。检测从 `Work = Available` 开始，逐轮查找每类需求均不超过 Work 的线程，模拟它完成并把 Allocation 加回 Work。所有线程可完成则接受请求；一整轮没有进展则拒绝，并撤销本次 Need。尚未执行的后续申请不计入当前 Need。

实际获取资源时，Available 减一、Need 减一、Allocation 加一。释放时归还许可；阻塞锁或信号量若有等待者，会在唤醒前直接完成资源交接，避免把已承诺给等待者的许可计作空闲。关闭检测时继续记账，后续开启可沿用当前状态。线程退出时清理它的行，防止复用 TID 继承旧记录。

`sys_enable_deadlock_detect` 接受 0 和 1，其他参数返回 -1。两个资源类别分别检测，符合本章作业范围。

## 三、问答题

### 1. 主线程退出时需要回收什么？其他线程控制块在哪里被引用？

主线程退出视为整个进程结束，需要结束所有线程。用户资源包括线程的用户栈、TrapContext 页面、TID，以及进程代码、数据、堆等地址空间资源；内核资源包括线程内核栈、任务控制块及进程管理的数据结构。文件描述符和同步对象所持引用也需要释放。

当前框架先取出线程的 `TaskUserRes`，释放 PCB 的可变借用后再销毁这些资源，因为释放 TID 和用户页需要再次访问 PCB。随后回收其余地址空间，清空文件表和线程表。PCB 的僵尸状态和退出码留给父进程通过 `waitpid` 读取及回收。

线程控制块使用 `Arc`，可能保存在以下位置：

| 引用位置 | 退出时的处理 |
| --- | --- |
| PCB 的 tasks 表 | 清除线程表项，释放进程持有的引用。 |
| 调度器就绪队列 | 移除该进程线程，避免已退出线程再次执行。 |
| 定时器等待队列 | 取消定时唤醒并释放引用。 |
| 锁、信号量、条件变量等待队列 | 随所属进程同步对象的销毁释放；它们持有的引用也会影响 TCB 最终释放时间。 |
| 处理器的 current、调度器的 stop_task | 当前线程仍使用内核栈，需保留引用到完成切换之后，再安全释放。 |
| 内核执行过程中的局部 Arc | 在相应作用域结束或显式 drop 时释放。 |

因此，清空 tasks 表只是回收的一部分；最后一个强引用消失时，TCB 及其内核栈才会析构。线程指向所属进程的是 Weak，不增加进程的强引用计数。

### 2. 两种 Mutex 实现有何区别，会导致什么问题？

`Mutex1::unlock` 先把 locked 置为 false，再唤醒一个等待者。被唤醒线程要在 lock 的循环中重新竞争锁；另一个线程可能抢先获得锁，使它再次入队。因此 while 循环是必要的。这种方式允许后来者插队，竞争激烈时等待者可能长期得不到锁。

`Mutex2::unlock` 在有等待者时保持 locked 为 true，并唤醒队首线程，相当于直接把锁交给它。被唤醒线程从阻塞点返回后已经拥有锁，因此 lock 使用 if 即可。没有等待者时才把 locked 置为 false。该方式按等待队列交接锁；获锁线程尚未运行时，其他线程仍需等待。

两者必须保持加锁和解锁策略配套。若采用 Mutex1 的解锁方式却只用 if 检查，等待者恢复时可能与抢先获锁者同时进入临界区；若采用 Mutex2 的交接方式却继续循环检查 locked，接收锁的线程会把自己的锁当作被占用，再次阻塞。
